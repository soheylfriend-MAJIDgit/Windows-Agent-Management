# ایجنت مدیریت — پنل ویندوز

پنل وب مدیریت و نظارت برای پروژه‌ی اتوماسیون ویندوزی «Windows-Agent».
این پنل **فقط ناظر** است: کدهای ایجنت همکار (`job_*.py`) را از گیت‌هاب می‌خواند، برای اجرای دوباره
کامیت کوچک می‌زند، پرامپت‌ها را به‌صورت فایل در مخزن همکار می‌گذارد و نتیجه‌ی اجراها را از
فایل‌های `logs` در گوگل درایو (یا ورود دستی) می‌خواند. هیچ‌چیز در مخزن مادر (`Windows-Agent`)
نوشته نمی‌شود و فایل‌های کنار `app.py` دست‌کاری نمی‌شوند.

- **زبان رابط:** فارسی، راست‌به‌چپ، فونت وزیرمتن، تاریخ شمسی و ساعت تهران (UTC+03:30)
- **میزبانی:** Cloudflare Workers با Next.js 16 و `@opennextjs/cloudflare`
- **پایگاه داده:** Cloudflare D1 با ساخت خودکار جدول‌ها؛ هیچ SQL دستی لازم نیست
- **خواندن گیت‌هاب:** بسته‌ی ZIP از `codeload.github.com` (بدون کلید API و بدون سقف ۶۰ درخواست در ساعت)
- **نوشتن گیت‌هاب:** GitHub Contents API با توکنی که فقط سمت سرور نگه‌داری می‌شود

## ۳) راه‌اندازی سریع (Cloudflare)

پیش‌نیاز: Node.js 22+، حساب Cloudflare، و (برای نوشتن) یک توکن گیت‌هاب.

```bash
npm install
npx wrangler login

# متغیرهای اختیاری/لازم را به‌صورت secret ثبت کنید:
npx wrangler secret put GITHUB_TOKEN            # برای اجرای دوباره و ارسال پرامپت
npx wrangler secret put MANAGER_PASSCODE        # اختیاری: قفل ورود پنل
npx wrangler secret put GOOGLE_SERVICE_ACCOUNT_JSON   # اختیاری: همگام‌سازی درایو
npx wrangler secret put GOOGLE_DRIVE_LOGS_FOLDER_ID    # اختیاری

npm run deploy
```

`npm run deploy` این کارها را انجام می‌دهد:

1. `opennextjs-cloudflare build` — ساخت بسته‌ی Worker.
2. `opennextjs-cloudflare deploy` — استقرار روی Cloudflare.
3. در اولین استقرار، Wrangler (نسخه ۴.۴۵+) دیتابیس D1 را **خودکار** می‌سازد و شناسه را در
   `wrangler.jsonc` می‌نویسد (قابلیت Automatic provisioning؛ در زمان نگارش open beta است).
4. جدول‌ها با اولین درخواست به سایت، خودکار ساخته می‌شوند (`ensureSchema`). هیچ
   `wrangler d1 migrations apply` یا SQL دستی لازم نیست.

> اگر حساب شما/نسخه‌ی Wrangler تأمین خودکار را انجام نداد:
> `npx wrangler d1 create windows-agent-management-cloudflare-db` را اجرا کنید و `database_id` را در
> `wrangler.jsonc` بگذارید؛ سپس دوباره deploy کنید.

پس از استقرار، آدرس `https://windows-agent-management-cloudflare.<subdomain>.workers.dev` را باز کنید.
برای secretها می‌توانید از پنل Cloudflare (Workers → Settings → Variables) هم استفاده کنید.
secretها فقط روی سرور در دسترس‌اند و هرگز در باندل کلاینت قرار نمی‌گیرند.

### استقرار از طریق داشبورد (Git / Workers Builds)

اگر می‌خواهید با هر push خودکار deploy شود، در داشبورد Cloudflare →
**Workers & Pages → Create → Connect to Git** این مقدارها را بگذارید:

| فیلد | مقدار |
| --- | --- |
| Project name | `windows-agent-management-cloudflare` (همان `name` در `wrangler.jsonc`) |
| Build command | `npm run build:worker` (یعنی `opennextjs-cloudflare build`؛ خالی نگذارید) |
| Deploy command | `npx wrangler deploy` |
| Preview command | `npx wrangler preview` — با روشن‌بودن «Builds for Preview branches»، هر push غیر از `main` یک Worker Preview مستقل می‌سازد |
| Path (Advanced) | `/` |

نکته‌های مهم:

- **Build command را خالی نگذارید.** فایل `.open-next/worker.js` که `main` در
  `wrangler.jsonc` است، در مخزن نیست و فقط با `opennextjs-cloudflare build` ساخته می‌شود؛
  `npm run build` به‌تنهایی کافی نیست.
- **شاخه‌ی production** باید همان شاخه‌ای باشد که کد در آن است. اگر کد روی شاخه‌ی
  `arena/...` است، در **Settings → Builds → production branch** همان را انتخاب کنید یا
  ابتدا آن را به `main` مرج کنید؛ وگرنه Build روی `main` خالی اجرا می‌شود.
- Workers Builds خودش `npm ci` را اجرا می‌کند؛ لازم نیست در Build command بنویسید.
  نسخه‌ی Node از `.nvmrc` (این مخزن: `22`) خوانده می‌شود و با `NODE_VERSION` هم قابل
  بازنویسی است.
- D1 به‌صورت draft binding با نام `DB` تعریف شده است. Wrangler در اولین deploy یک
  دیتابیس اختصاصی با نام `windows-agent-management-cloudflare-db` می‌سازد و آن را وصل
  می‌کند. Build token باید مجوز D1 داشته باشد؛ توکن خودکاری که این فرم می‌سازد معمولاً
  این مجوز را دارد.
- برای Previewها، در **Settings → Builds → Previews Base** گزینه‌ی
  **Builds for Preview branches** را روشن کنید. تنظیمات Preview از Production ارث نمی‌رسد؛
  متغیرها را import و binding `DB` را ترجیحاً به یک D1 آزمایشی جدا وصل کنید.
- متغیرهای این فرم **build variables** هستند. `GITHUB_TOKEN` و بقیه‌ی secretها باید
  **runtime secret** باشند: بعد از اولین deploy از
  **Worker → Settings → Variables and Secrets** یا با `wrangler secret put`.

نسخه‌ی دستی جدول‌ها (اختیاری، برای بازیابی/مستندسازی):

```bash
npm run db:remote     # wrangler d1 execute ... --file=migrations/0001_init.sql
npm run db:local      # روی D1 محلی
```

### اجرای محلی

```bash
cp .dev.vars.example .dev.vars   # و GITHUB_TOKEN را بگذارید
npm install
npm run dev                      # http://localhost:3000 با D1 محلی
```

`initOpenNextCloudflareForDev` باعث می‌شود bindingهای `wrangler.jsonc` (از جمله `DB`) در
`next dev` هم شبیه‌سازی شوند. داده‌های محلی D1 در `.wrangler/state` نگه‌داری می‌شوند.

```bash
npm run preview    # build + اجرای Worker روی wrangler (نزدیک‌ترین حالت به production)
npm run build      # build معمول Next.js
npm run typecheck  # tsc --noEmit
npm run lint:job -- --dir .   # بررسی AST فایل‌های job_*.py (اختیاری)
```

| `MOTHER_OWNER` / `MOTHER_REPO` / `MOTHER_BRANCH` | اختیاری | پیش‌فرض مخزن مادر (فقط نمایشی/خواندنی). |

## ۴) گیت‌هاب

### خواندن (بدون کلید)
بسته‌ی شاخه از این آدرس گرفته می‌شود:

```
https://codeload.github.com/{owner}/{repo}/zip/refs/heads/{branch}
```

سپس فقط فایل‌های **ریشه** با الگوی `job_*.py` جدا می‌شوند؛ نام، حجم، تعداد خط، اولین خط
توضیح، هش محتوا و زمان فایل از داخل ZIP استخراج می‌شود. نتیجه ۴۵ ثانیه در حافظه و
به‌صورت اسنپ‌شات در D1 کش می‌شود تا با قطعی موقت گیت‌هاب، فهرست از بین نرود.

اگر `GITHUB_TOKEN` موجود باشد، تاریخ آخرین کامیت هر فایل با GitHub API (حداکثر ۸ درخواست در
هر بار، با کش ۱۰ دقیقه‌ای در D1) تکمیل می‌شود. این کار سقف ۶۰ درخواست در ساعتِ بدون توکن را
مصرف نمی‌کند و با توکن (۵۰۰۰ درخواست در ساعت) کاملاً کافی است.

### نوشتن
- **اجرای دوباره:** یک کامیت کوچک که خط `# rerun: <تاریخ شمسی> <ساعت تهران> — <کد>` را
  به **بالای محتوای فایل** اضافه می‌کند. هر بار کد تصادفی تازه‌ای تولید می‌شود تا حتی دو
  اجرای پشت‌سرهم هم محتوای متفاوت داشته باشند.
- **ارسال اختصاصی به Arena:** حالت پیش‌فرض، متن را عیناً در `PROMPT_TEXT` فایل ثابت
  `job_arena.py` می‌گذارد و برای هر ارسال یک `PROMPT_REQUEST_ID` یکتا ثبت می‌کند. پنل ویندوز
  فایل را دریافت و اجرا می‌کند؛ اسکریپت Arena متن را در کادر گفتگو Paste و ارسال می‌کند و طبق
  انتخاب فرم، نتیجه‌ی موفق/ناموفق را از راه `bot_api.json` به مقصد پیش‌فرض تلگرام می‌فرستد.
- **حالت‌های پیشرفته:** همچنان می‌توان فایل جدید `job_<slug>.py` ساخت (داک‌استرینگ = پرامپت)
  یا متن پرامپت را به انتهای فایل موجود به‌صورت کامنت اضافه کرد.

توکن فقط در Route Handlerها خوانده می‌شود؛ در پاسخ API، HTML، URL یا `NEXT_PUBLIC_*` قرار
نمی‌گیرد. صفحه‌ی تنظیمات تنها «تنظیم شده / تنظیم نشده» را نشان می‌دهد.

## ۵) اجرای دوباره چطور کار می‌کند؟

`app.py` برای هر فایل در `CODES` یک حالت ذخیره می‌کند که شامل **هش SHA-256 هشت‌رقمی** محتواست.
در هر بررسی، اگر هش محتوای دانلودشده با هش ذخیره‌شده فرق کند، فایل در `CODES` بازنویسی و
دوباره اجرا می‌شود. بنابراین:

- افزودن/تغییر یک خط کامنت، هش را عوض می‌کند و اجرای دوباره را قطعی می‌کند. ✅
- تغییر `version.txt` فقط نسخه‌ی خود برنامه را عوض می‌کند و **هیچ اجرایی را تحریک نمی‌کند**. ❌
- کامیت خالی (بدون تغییر محتوا) هم اثری ندارد.

پنل بعد از کامیت موفق، اسنپ‌شات را باطل می‌کند و رویداد «درخواست اجرای دوباره» را با لینک
کامیت ثبت می‌کند. وضعیت فایل تا رسیدن نتیجه، «در انتظار» می‌ماند.

## ۶) قواعد فایل‌های `job_*.py`

| قاعده | بررسی در پنل |
| --- | --- |
| فقط در **ریشه‌ی** مخزن | مسیر داخل ZIP باید دقیقاً دو بخش داشته باشد |
| نام با `job_` و پسوند `.py` | `^job_[A-Za-z0-9_]+\.py$` |
| فقط کتابخانه‌ی استاندارد پایتون ۳.۹+ | فهرست ماژول‌های استاندارد در سرور؛ import نسبی و import پویا ممنوع |
| بدون `input()` / `getpass()` / `stdin` | تحلیل توکن‌های کد (بدون رشته/کامنت) |
| حداکثر ۶۰۰ ثانیه | `time.sleep(n)` با `n > 600` خطا؛ `while True` بدون `break` هشدار |
| بدون مسیر مطلق ویندوزی (`C:\Users\...`) | در کد تازه **خطا**؛ در فایل‌های موجود فقط **هشدار** |
| خروجی متنی با `print()` | نبود `print` هشدار |
| حجم حداکثر ۵۱۲ کیلوبایت | بررسی بایت واقعی |

بررسی‌ها در `src/lib/lint.ts` (تحلیل سبک و سازگار با Worker) انجام می‌شود. برای AST واقعی
پایتون، اسکریپت اختیاری `scripts/lint_job.py` در مخزن است:

```bash
python3 scripts/lint_job.py --dir .        # همه‌ی job_*.py ریشه
python3 scripts/lint_job.py job_x.py --strict
```

هشدارها مانع کامیت نمی‌شوند؛ خطاها در فرم پرامپت مانع ارسال‌اند و در فهرست کدها با نشان
قرمز دیده می‌شوند.

## ۷) فرمت فایل‌های لاگ

### نتیجه‌ی اجرا — `logs/<job>_result.txt`
```
نتیجه اجرای کد Arena
==============================================================
فایل: job_wikipedia.py
شروع: ۱ آبان ۱۴۰۵ — ۲۳:۵۰:۱۲ تهران
مدت: 12.5 ثانیه
کد خروج: 0

----- خروجی -----
...

----- خطاها -----
(خالی)
```

پنل زمان شروع را از متن شمسی می‌خواند (با پشتیبانی از ارقام فارسی/عربی و چند قالب)،
مدت و کد خروج را جدا می‌کند و بخش‌های `(خالی)` را خالی حساب می‌کند. اگر زمان شروع در فایل
نبود، زمان تغییر فایل درایو جای آن استفاده می‌شود.

### فایل خطا — `logs/errors/errors_<تاریخ>.txt`
بلوک‌ها با خط ۶۲ کاراکتری `=` جدا می‌شوند و هر بلوک شامل `زمان:`، `موضوع:`،
`نسخه برنامه:` و متن جزئیات است. هر بلوک با انگشت‌نگاری SHA-256 یکتا می‌شود تا همگام‌سازی
تکراری، رکورد تکراری نسازد.

همه‌ی زمان‌های نمایش، شمسی و ساعت تهران هستند؛ ذخیره‌سازی در D1 به‌صورت ISO و UTC است.
ورود دستی هم دقیقاً همین پارسرها را استفاده می‌کند و برای فایل‌های قدیمی/کپی‌شده کار می‌کند.

## ۸) گوگل درایو (اختیاری)

۱. در Google Cloud یک پروژه بسازید و **Google Drive API** را فعال کنید.
۲. یک Service Account بسازید و کلید JSON بگیرید.
۳. پوشه‌ی `Windows-Agent-DB/logs` (یا خود `Windows-Agent-DB`) را با ایمیل حساب سرویس،
   دسترسی **Viewer** به اشتراک بگذارید.
۴. شناسه‌ی پوشه را از انتهای آدرس `drive.google.com/drive/folders/<ID>` بردارید و به‌همراه
   JSON به‌عنوان secret ثبت کنید:

```bash
npx wrangler secret put GOOGLE_SERVICE_ACCOUNT_JSON < service-account.json
npx wrangler secret put GOOGLE_DRIVE_ROOT_FOLDER_ID
```

پنل با JWT (RS256، امضاشده با Web Crypto) از حساب سرویس توکن می‌گیرد، فایل‌های تازه را
می‌خواند و در D1 ذخیره می‌کند. همگام‌سازی خودکار حداکثر هر چند دقیقه و فقط وقتی پنل باز است
اجرا می‌شود؛ دکمه‌ی «همگام‌سازی درایو» هم به‌صورت دستی کار می‌کند.

اگر درایو را وصل نکنید، همه‌چیز باز است و می‌توانید متن فایل نتیجه/خطا را در صفحه‌ی
گزارش‌ها **دستی** وارد کنید (تشخیص نوع فایل خودکار است).

## ۹) داده‌ها (D1)

| جدول | محتوا |
| --- | --- |
| `jobs` | اسنپ‌شات کدها: نام، حجم، خطوط، داک‌استرینگ، محتوا، هش، تاریخ/شناسه‌ی کامیت، وضعیت حضور |
| `runs` | هر نتیجه‌ی اجرا: کد، زمان شروع، مدت، خروجی، خطا، منبع (drive/manual)، متن خام |
| `error_logs` | بلوک‌های فایل‌های خطا با انگشت‌نگاری یکتا |
| `prompts` | پرامپت‌های ارسالی: حالت، متن، کد، کامیت، وضعیت |
| `events` | رویدادهای نمایشی داشبورد (اجرای دوباره، پرامپت، همگام‌سازی، ورود دستی) |
| `settings` | بازنویسی مالک/مخزن/شاخه و تنظیمات همگام‌سازی |
| `sync_state` | زمان/خطای آخرین همگام‌سازی درایو |

با `ALTER TABLE` در همان آرایه).

## ۱۰) API

| متد و مسیر | کار |
| --- | --- |
| `GET /api/overview` | آمار، آخرین کدها/اجراها، رویدادها، سلامت اتصال‌ها |
| `GET /api/jobs` | فهرست کدها (`?refresh=1` برای دور زدن کش، `?enrich=0` برای صرف‌نظر از تاریخ کامیت) |
| `GET /api/jobs/[name]` | محتوا و جزئیات یک کد |
| `GET /api/jobs/[name]/download` | دانلود فایل `.py` |
| `POST /api/jobs/[name]/rerun` | کامیت اجرای دوباره؛ `{"dryRun":true}` فقط پیش‌نمایش |
| `POST /api/lint` | بررسی قواعد یک قطعه کد |
| `GET/POST /api/prompts` | تاریخچه/ارسال پرامپت؛ حالت `arena` با `telegramMode=off|final|start_final` و `dryRun` برای پیش‌نمایش فایل |
| `GET /api/reports?type=results\|errors` | گزارش‌ها با فیلتر `q`، `range`، `status`، یا `date=YYYY-MM-DD` (روز جلالی به وقت تهران) |
| `POST /api/sync` | همگام‌سازی گوگل درایو (`force`, `limit`) |
| `POST /api/ingest` | ورود دستی متن نتیجه/خطا (`fileName`, `content`, `kind?`, `modifiedAt?`) |
| `GET/PUT /api/settings` | خواندن/ذخیره‌ی مخزن‌ها و تنظیم همگام‌سازی |
| `GET /api/health?deep=1` | بررسی اتصال D1، توکن، گیت‌هاب، درایو، ورود |
| `GET /api/database` | وضعیت تفصیلی D1: binding، schema، جدول‌ها، ایندکس‌ها و تعداد رکوردها |
| `GET /api/session` | وضعیت قفل ورود |
| `POST /api/auth/login` / `logout` | ورود/خروج مدیر (کوکی HttpOnly، SameSite=Lax) |

همه‌ی خطاها به شکل `{"error":{"code","message","hint"}}` و با پیام فارسی برمی‌گردند.

## ۱۲) امنیت و محدودیت‌ها

- توکن گیت‌هاب و کلید گوگل فقط سمت سرور؛ هیچ متغیر محیطی به کلاینت تزریق نمی‌شود.
- ورود اختیاری با `MANAGER_PASSCODE`؛ کوکی `HttpOnly`، امضای HMAC-SHA256، عمر ۷ روز و
  محدودیت ۱۰ تلاش ناموفق در ۵ دقیقه برای هر IP.
- پاسخ‌های API با `Cache-Control: no-store` و `X-Content-Type-Options: nosniff`.
- نوشتن‌ها فقط روی مخزن همکار و مسیرهای `job_*.py` ریشه انجام می‌شوند؛ مخزن مادر در کد
  هیچ مسیر نوشتنی ندارد.
- تحلیل قواعد در Worker، تحلیل سبک است (نه AST کامل پایتون). برای اطمینان بیشتر از
  `scripts/lint_job.py` استفاده کنید. پنل ادعای اجرای کامل مفسر پایتون را ندارد.
- همگام‌سازی خودکار به باز بودن پنل وابسته است (بدون Cron Trigger)؛ برای نتیجه‌ی فوری از
  دکمه‌ی همگام‌سازی یا ورود دستی استفاده کنید.
- دکمه‌های نوشتن بدون توکن غیرفعال می‌شوند و پنل حالت «فقط خواندن» را نشان می‌دهد.
